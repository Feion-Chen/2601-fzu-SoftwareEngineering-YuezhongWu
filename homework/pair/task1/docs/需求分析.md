# 校园失物招领小程序需求分析

## 一、项目背景

在校园生活中，校园卡、钥匙、水杯、雨伞、耳机和书籍等物品遗失十分常见。目前失物和招领信息主要分散在班级群、宿舍群和朋友圈中，信息容易被后续聊天覆盖，发布者与失主之间也缺少统一、便捷的检索渠道。因此，需要设计一个面向校园学生的失物招领小程序，将寻物与招领信息集中展示，提高物品归还效率。

## 二、目标用户与需求

### 1. 遗失物品的学生

核心需求是快速发布寻物信息，说明物品名称、遗失地点、时间和联系方式；同时能够通过搜索查看是否有人发布对应招领信息。用户希望操作步骤少、信息发布快、联系方式可见但不要求即时聊天。

### 2. 捡到物品的学生

核心需求是发布招领信息，上传物品名称、拾取地点、时间和简要描述，并在物品归还后修改状态。用户希望发布过程简单，不必填写过多敏感信息。

### 3. 浏览信息的学生

核心需求是集中查看校园内的失物和招领信息，通过关键词、类型和地点缩小范围，再进入详情页面确认物品特征并联系发布者。

## 三、主要问题与解决方案

| 现实问题 | 设计解决方式 |
| --- | --- |
| 信息分散在多个群聊中 | 提供统一的信息列表和固定入口 |
| 群消息更新快，旧消息难找 | 支持按物品名称搜索和按类型筛选 |
| 信息缺少统一字段 | 统一记录物品名称、类型、地点、时间、描述和联系方式 |
| 物品已经归还但信息仍保留 | 在“我的发布”中提供状态修改功能 |
| 涉及隐私，不宜公开过多信息 | 联系方式由发布者主动填写，原型不设计即时聊天和定位 |

## 四、功能范围

### 基础功能

1. 浏览首页信息，区分全部、寻物、招领。
2. 发布寻物信息。
3. 发布招领信息。
4. 按关键词搜索物品。
5. 按物品类型和地点进行简单筛选。
6. 查看物品详情。
7. 查看发布者提供的联系方式。
8. 在“我的发布”中修改物品状态。

### 暂不实现的功能

为了保持原型简单，并与第二次结对作业衔接，本次不设计实名认证、即时聊天、地图定位、复杂后台审核、积分体系和消息推送。

## 五、核心业务流程

### 流程一：浏览信息并联系发布者

学生进入首页，浏览或搜索物品信息，选择感兴趣的条目进入详情，核对物品描述和地点，最后通过页面中的联系方式联系发布者。

### 流程二：发布信息

学生进入发布页面，选择“寻物”或“招领”，填写物品名称、类型、地点、时间、描述和联系方式，确认信息后点击发布，系统显示发布成功页面，并将信息加入“我的发布”。

### 流程三：修改信息状态

学生在“我的发布”页面找到已发布的信息，将状态从“寻找中”改为“已找到”，或将“招领中”改为“已归还”，避免他人继续无效联系。

## 六、页面信息结构

| 页面 | 主要信息 | 主要操作 |
| --- | --- | --- |
| 首页 | 搜索框、分类标签、信息卡片 | 搜索、切换分类、查看详情 |
| 搜索页 | 关键词、筛选条件、结果列表 | 修改关键词、筛选、查看详情 |
| 详情页 | 物品图片、名称、类型、地点、时间、描述、联系方式 | 联系发布者、返回 |
| 发布页 | 寻物或招领类型、物品表单、图片占位 | 填写、提交 |
| 发布成功页 | 成功提示、发布摘要 | 查看我的发布、返回首页 |
| 我的发布页 | 自己发布的信息和当前状态 | 修改状态、查看详情 |

## 七、非功能需求

- 易用性：页面层级不超过三层，核心操作按钮固定在显眼位置。
- 清晰性：使用统一卡片结构和状态标签，信息优先展示名称、地点和时间。
- 一致性：发布寻物和招领信息共用一套表单结构。
- 安全性：只展示发布者主动填写的联系方式，不设计公开校园卡号等敏感信息。
- 可扩展性：后续可以接入登录、数据库、图片上传和信息审核功能。

## 八、需求结论

校园失物招领小程序的核心价值是集中信息、方便检索和快速联系。第一版原型应优先保证发布、浏览、搜索、详情和状态修改闭环完整，界面操作简单，避免使用与核心目标无关的复杂功能。
